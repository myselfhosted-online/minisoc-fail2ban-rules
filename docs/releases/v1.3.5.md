# MiniSOC Fail2Ban Rules v1.3.5 — Runtime Compatibility and Upgrade Safety

This maintenance release fixes the signature database migration failure introduced in v1.3.4 and improves the safety of upgrades on systems with customized Fail2Ban configurations. **It does not automatically replace operator-maintained filters or restart the MiniSOC application.**

## What was fixed

### 1. Incorrect runtime signature format

The public repository stores rules as `id|severity|category|regex`. The production MiniSOC correlator reads `/etc/minisoc/signatures-v2.db` as `category|severity|regex` using `raw.split('|', 2)`.

The v1.3.4 updater incorrectly treated repeated runtime categories such as `secret` and `repository` as duplicate public IDs, producing `Duplicate signature ID secret` and preventing the update. Disabling the duplicate check alone would also have risked appending unreadable four-column rows. **v1.3.5 converts bundled rules to the three-column runtime format before merging them.**

### 2. Safe, idempotent database merging

- Keep existing local signature lines, comments, severities, and classifications byte-for-byte.
- Preserve regex alternations containing `|`; only the first two separators have structural meaning in the runtime format.
- Append a bundled regex only if that exact pattern is absent; local definitions take precedence.
- Reject malformed bundled rules and preserve structurally incompatible local databases for review.
- Preserve atomic file replacement, a restricted pre-update backup, and automatic rollback on update failures.

### 3. Existing jail configuration protection

If `nginx-skanery` or `nginx-dev-honeypot` is already defined in standard `jail.conf`, `jail.local`, or `jail.d/*.conf` / `*.local` files, the installer does not create a competing bundled default jail configuration. This protects custom `maxretry`, `bantime`, and other jail settings.

### 4. No unnecessary Fail2Ban reload

When only the external MiniSOC signature database changes, the installer no longer validates or reloads unchanged Fail2Ban jails. Changes to Fail2Ban filters or jail files still receive configuration validation, reload, backup, and rollback protection.

## Verification

- 75 local updater, compatibility, regression, and rollback tests passed.
- GitHub Actions validation with the real Fail2Ban parser passed.
- On Debian 13, the operator completed a successful database-only installation without altering customized filters or jail configuration.
- `fail2ban-client -t` reported a successful configuration test.
- The production MiniSOC correlator loaded **88 of 88 runtime signatures across 19 categories, with zero skipped entries**.
- A subsequent dry-run proposed no additional changes, confirming idempotence for the tested configuration.

## Upgrade guidance

Download the release archive, verify its checksum against `SHA256SUMS.txt`, and inspect the planned changes before applying them:

```bash
sudo bash install/install.sh --dry-run
```

If you maintain customized filters and explicitly want to preserve them while updating compatible files, use:

```bash
sudo bash install/install.sh --dry-run --preserve-custom-filters
sudo bash install/install.sh --preserve-custom-filters
```

**Important:** With `--preserve-custom-filters`, the bundled v1.3.5 Fail2Ban filter rules are **not activated** for any filter reported as preserved. Review and merge those filters separately if you want the new blocking rules. The MiniSOC application is not restarted by the installer; reload its signature cache separately only if your deployment requires it.

**Upgrade advisory:** Do not use the v1.3.4 installer against a production three-column MiniSOC runtime database. Upgrade to v1.3.5 and review `--dry-run` output first.
