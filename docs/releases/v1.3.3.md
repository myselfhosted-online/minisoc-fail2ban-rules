# MiniSOC Fail2Ban Rules v1.3.3

**Maintenance release — safer handling of customized Fail2Ban filters**

## Why this release is necessary

The v1.3.2 updater rejected certain valid operator-maintained `nginx-skanery.conf` filters with the misleading message `unknown baseline or git unavailable`, even when Git was installed and available to root. The updater assumed that every compatible scanner filter must contain one literal `.git` regex fragment; legitimate local expressions can use different but overlapping syntax, such as `(config|HEAD)` instead of an upstream non-capturing group. This release corrects that detection defect without weakening the protection against overwriting custom Fail2Ban rules.

## Bugs fixed

1. **False rejection by literal fingerprint:** removed hard-coded assumptions about the textual spelling of `.git` indicators. Known baselines are now considered directly during three-way merge evaluation.
2. **Incomplete upgrade baseline coverage:** added the verified v1.3.2 release filters to the bundled historical baselines. Existing unmodified v1.3.2 installations are recognized without requiring Git.
3. **Unclear manual-review diagnosis:** distinguished a clean merge from an unknown/conflicting local filter. The dry run reports preserved filters and explicitly states that new upstream filter rules are not activated for them.
4. **All-or-nothing upgrade blocker for independent components:** added an explicit `--preserve-custom-filters` choice. It permits updating other managed files while leaving incompatible operator-maintained filters unchanged, with backup, post-update Fail2Ban validation, reload, and rollback.
5. **Regression coverage gap:** added synthetic tests for the reported custom-regex format and for partial-update rollback safety.

## Safety behavior

- **No automatic replacement of unrelated custom rules.** Clean, unambiguous three-way merges must retain the bundled upstream `failregex`; otherwise the custom filter is preserved for manual review.
- **No silent partial upgrades.** Without `--preserve-custom-filters`, the installer still stops before writing any files if a custom filter cannot be merged.
- **No change to active detection policy.** This release does not add new one-hit ban signatures or modify operator jail settings.
- **No automatic production deployment.** Downloading or publishing the archive does not modify a Debian host.

## Upgrade guidance

Review the plan from the extracted official release:

```bash
sudo bash ./install/install.sh --dry-run
```

If the plan identifies an unmergeable custom filter, preserve it and update only the remaining managed components **by explicit choice**:

```bash
sudo bash ./install/install.sh --dry-run --preserve-custom-filters
sudo bash ./install/install.sh --preserve-custom-filters
sudo fail2ban-client -t
```

This is **not** a full filter upgrade: a preserved `nginx-skanery.conf` continues to use its previous rules. To adopt the new upstream filter signatures, review its differences and perform a supervised migration with independent `fail2ban-regex` testing. Do not blindly replace custom regexes.

## Validation

- Unit and regression tests cover recognized source baselines, customized filters, dry-run behavior, explicit partial updates, backup manifests, rollback, and uninstaller protections.
- GitHub Actions validates the release using a real Fail2Ban parser. Local Python-only tests do not substitute for that integration check.
